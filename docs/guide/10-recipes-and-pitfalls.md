# 常用提示範本與常見避坑

以下彙整值得直接複製的實戰 Prompt，以及初學者最容易踩中的認知陷阱。實務操作時直接替換路徑與完成條件即可。

## 1. 高頻實用 Prompt 範本

### 發送前打磨提示詞深度與對齊目標
```text
/sharpen 幫我撰寫新版計費服務的入職引導文件。
```
[`sharpen`](../../.agents/skills/sharpen/SKILL.md) 會先指出領域頂尖專家會多做哪些你沒要求的事、從哪個第一手素材開始、用什麼工具與客觀驗證信號，接著把你的提示詞重寫為深度版本交還給你（不會直接執行任務）。確認重寫無誤後即可發送執行。

```text
/in-your-own-words
```
在開始複雜改動前，讓 [`in-your-own-words`](../../.agents/skills/in-your-own-words/SKILL.md) 先用 Agent 自己的話複述你的核心目標與底層問題，第一時間攔截認知偏差。

### 理解陌生的複雜模組
```text
先用 /how 梳理這套初始化機制的運行流程，再用 /why 調查它近期被修改破壞的原因。
```
先搞懂機制，再探究歷史。技能回報時會明確列出引用的來源，讓你知道結論是基於哪些代碼或歷史記錄。

### 獲取設計的第二意見 (Second Opinion)
```text
讓 /arena 對目前的架構思路提供第二意見，比較既有方案與其他可能架構。
```
當前的設計將作為候選方案之一參與競技，評審綜合報告會告訴你競技場是否發現了更優雅的做法。

### 平行執行矩陣切片檢查
```text
/swarm 檢查 packages/ 下的所有套件，每個套件由獨立 worker 跑 check.sh，最後匯總單一報告。
```
每個子代理獨立鎖定單一範圍，主代理直接過濾中間冗長日誌，回傳整齊的 `PASS`、`ISSUES` 或 `BLOCKED` 匯總表。

### 對分支進行嚴苛的紅隊實機擊穿審查
```text
/interrogate 審查整個分支，嚴格挑刺。先不要修改代碼，非真實缺陷或行為回歸的瑣碎風格問題一律忽略。
```
透過明確的約束避免噪音：每位審查員必須以實際執行證明缺陷，主代理重跑驗證後僅保留確鑿的缺陷，並一併列出被剔除（`Dropped`）的項目與原因。

### 測試驅動修復 Bug
```text
/poteto-mode 先重現重複寫入問題。如果有低成本本機測試路徑就使用 /tdd，修復後重新驗證。
```
明確指出「若有低成本路徑」，給予 Agent 彈性，避免為脆弱的外部依賴編寫龐大虛假的 Mock。

### 隔夜無人值守與歸來快速同步
```text
我要去休息了。使用 /goal 持續自主推進，直到所有 fixtures 測試全綠。記錄 decisions.tsv 供早晨審核。
```
當你回來時，直接輸入：
```text
/ketchup
```
[`ketchup`](../../.agents/skills/ketchup/SKILL.md) 會在 150 字內搭配截圖與圖表幫你抓出進展重點，並完整列出正等待你拍板的決策事項與建議選項。若想看帶字幕的幻燈片短片摘要，則可輸入 [`/ketchup-video`](../../.agents/skills/ketchup-video/SKILL.md)。

### 根除重複發生的 Agent 錯誤
```text
/correct
```
[`correct`](../../.agents/skills/correct/SKILL.md) 會找出 Agent 反覆犯下的錯誤類別，優先透過架構、強型別或 Linter 從結構上封死錯誤路徑。

### 單行即時原則糾偏
```text
我說的是先重現問題，還沒讓你動手修復代碼。
```
```text
遵守 Prove It Works 原則。給我看真實終端輸出，而不是 build 通過的 log。
```
```text
套用 Attack the Premise。這已經是第二次修同一個地方失敗了，先寫下並測試你的前提假設。
```
```text
/unslop 整理剛才的 PR 說明，去除陳腔濫調。
```

### 請求白話翻譯
```text
/bro
```
這就是整個 Prompt。[`bro`](../../.agents/skills/bro/SKILL.md) 會把剛才充滿生硬術語與冗長細節的技術回覆，翻譯成正常人類隨口交談的大白話。

## 2. 必看避坑指南 (The Pitfalls)

1. **在 Prompt 裡手動排定技能清單**：
   「先用 /how 再用 /architect 然後 /arena...」只會打亂 Playbook 內建的最佳順序。只要說明**目標與邊界條件**，讓劇本自動編排。
2. **模糊的完成條件**：
   「把它變好一點」或「跑 4 個小時」無法作為判定依據。完成條件必須是**非真即假（Pass or Fail）**的客觀命令或檔案產物。
3. **多個平行 Agent 擠在同一個目錄**：
   互相覆寫檔案會導致工作區成為災難。需要平行攻堅時，務必宣告「各嘗試使用獨立 worktree」。
4. **把 `/arena` 當作覆蓋工具**：
   `/arena` 是「同一道題目多個方案競技，最後挑選最優並嫁接」；如果是「批次檢查多個獨立套件」，請使用 `/swarm`。
5. **對 Review 意見全盤照收**：
   機器人與人類都會在同一份清單中夾雜真實問題與雜訊。`/interrogate` 只保留經重跑指令證實的真實缺陷，並清楚列出被剔除（`Dropped`）的項目與理由；Babysit 亦具備附反證駁回雜訊的機制。
6. **以為編譯通過就是成功**：
   編譯只代表語法合法。始終要求真實的指令執行、介面走讀或資料回讀證據。
7. **直接手寫修改 `SKILL.md`**：
   技能面向的是未來的 Agent，一個不良的句子會成為未來錯誤的根源。透過 Authoring Playbook 或 Eval 劇本進行規範驗證。
