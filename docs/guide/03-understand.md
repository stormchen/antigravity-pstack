# 變更前深入理解代碼

修改你不理解的代碼，往往是引發隱蔽回歸（Regression）的主要原因。pstack 提供了四種不同的探索切入維度：`/how` 解釋代碼現在如何運作；`/why` 挖掘代碼被寫成這樣的歷史動機；`/teach` 將兩者融合為通俗易懂的解釋；`/recall` 則協助你重建在特定主題上的近期上下文。

![偵探用放大鏡研究機械藍圖，機器人搬運案件卷宗，後方黑板上連接各項線索。](./images/understanding.jpg)

---

## 1. 透過 `/how` 追蹤執行流程與機制

```text
/how 我們是如何進行通知去重的？查詢訂閱者時是否存在 N+1 查詢問題？
```

提出你心中真實的技術疑問。[`how`](../../.agents/skills/how/SKILL.md) 會深入檢視代碼，以「資深工程師為你進行模組導覽」的角度回答，清晰列出運行期流程、核心型別與非直覺的關鍵邏輯。若面對大型子系統，它會自動派發平行唯讀 Subagent 分頭探索；若只是狹窄的問題，則直接精準分析。

`/how` 亦支援**架構批判模式 (Critique Mode)**，適用於你懷疑現有模組劃分不合理時：

```text
/how 解釋同步服務的運作方式，並批判性審查其權責與邊界劃分。
```

這能確保批判始終扎根於實際代碼運作方式之上，而非憑空臆測。

---

## 2. 透過 `/why` 探尋設計決策與歷史脈絡

```text
/why 當初為什麼把重試上限設為 5 次？這個理由在目前架構下仍然成立嗎？
```

[`why`](../../.agents/skills/why/SKILL.md) 像是一位調查懸案的冷案偵探。它從 Git 提交歷史出發，並平行檢索 Issue 記錄、設計文件、錯誤追蹤與系統指標。產出的報告會明確區分**直接證據**與**推論分析**，並在記錄不足時標記為「看起來是」。如果歷史上無人記錄原因，它也會如實回報——因為「當初無人記錄原因」本身就是一個關鍵事實。

這兩個技能天然相輔相成。例如：`先執行 why 查出歷史背景，再用 how 說明現況` 是極為實用的組合。

---

## 3. 透過 `/teach` 真正吃透複雜改動

```text
/teach 讓我徹底理解這個 PR 是如何改變重試機制的。說服我它確實修復了根本原因，而不是僅僅治標。
```

[`teach`](../../.agents/skills/teach/SKILL.md) 適用於簡單摘要無法滿足深度的情境。它綜合 `/how` 與 `/why` 的調查成果，編織成由淺入深、搭配圖表流程的完整說明。「說服我」的視角尤為關鍵——它能把單純的代碼導覽轉換為具備技術論點的辯護，讓你能夠精確挑出邏輯漏洞。

---

## 4. 透過 `/recall` 喚醒個人近期進度

```text
/recall 幫我彙整上週處理匯出功能的進展與目前狀態。
```

[`recall`](../../.agents/skills/recall/SKILL.md) 梳理近期的會話歷史、提交紀錄與待處理問題，向你回報精準的事態摘要與下一步建議，適合你在休假或切換專案後重新拾起進度。

---

## 5. 接手前人工作：會話接續劇本 (Session Pickup)

當其他 Agent 或你在數天前留下了一個進行到一半的分支：

```text
/poteto-mode 接手這個分支。讀取決策日誌，搞清楚哪些已完成，從未完成處繼續，不要重做已完成的工作。
```

[會話接續劇本 (Session pickup)](../../.agents/skills/poteto-mode/playbooks/session-pickup.md) 會將先前的決策日誌視為權威依據，重建分支狀態並指出精確的復工點，直接在既有成果上驗證並推進。

> [!TIP]
> **避坑提醒**：切忌因為「反正 Agent 稍後會讀代碼」而略過理解步驟。缺乏整體概念就直接動手改寫的 Agent，往往會在第一個看起來合理的表面位置貼上症狀補丁，進而埋下更大的隱患。
