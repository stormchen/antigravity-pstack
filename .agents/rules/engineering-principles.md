# 核心工程與架構原則守則 (Engineering Principles & Rules)

本規則收錄專案的核心架構哲學與工程紀律。所有 Agent 及 Subagent 在規劃、設計架構、編寫代碼、重構與驗證時，均須嚴格遵循以下五大維度共 24 項原則。

---

## 一、核心思維原則 (Core Principles)

### 1. 惰性協議 (Laziness Protocol)
* **觸發情境**：重構、評估 Diff 大小、或想要新增抽象層與包裝時。
* **核心規範**：始終偏向刪除代碼與最簡變更。代碼越少，未來維護者的心智負擔越小。避免為了「未來的擴展性」引入當前不需要的介面、工廠或轉發層。

### 2. 加法前先做減法 (Subtract Before You Add)
* **觸發情境**：在現有系統上添加新功能或進行功能擴充時。
* **核心規範**：先清理死代碼、移除過時分支與簡化既有結構，使基底乾淨後再在其上建構新邏輯。絕不在雜亂的基礎上疊床架屋。

### 3. 最小化閱讀負擔 (Minimize Reader Load)
* **觸發情境**：撰寫或重構容易使人迷失的複雜代碼時。
* **核心規範**：壓縮間接層級，消除單一呼叫方的轉發封裝 (Collapse one-caller wrappers)；縮小可變狀態作用域 (Shrink mutable scope)。若追蹤一個執行流程需跨越超過 3 個檔案，應主動壓平層級。

### 4. 基石思維 (Foundational Thinking)
* **觸發情境**：撰寫業務邏輯之前。
* **核心規範**：核心資料結構優先於運算邏輯；定義好骨架與契約 (Scaffold-first)，後續開發僅是向穩定契約填入實現。明確並發參與者之間的共用關係。

### 5. 第一性原理重構 (Redesign from First Principles)
* **觸發情境**：將新需求融入既有架構時。
* **核心規範**：將新需求視為系統「第一天就存在」的核心約束來重新思考架構，而非僅在現有代碼上附加特殊條件分支 (`if-else`)。

### 6. 成果導向執行 (Outcome-Oriented Execution)
* **觸發情境**：架構重寫與大型遷移任務。
* **核心規範**：直接朝目標架構收斂，不要耗費精力構建臨時的中間相容過渡層；若需階段性破壞性變更，應有清晰範圍定義並迅速推進至目標狀態。

### 7. 體驗優先 (Experience First)
* **觸發情境**：產品、互動與功能範疇的取捨。
* **核心規範**：在使用者體驗與實現便利性衝突時，始終選擇為終端使用者帶來乾淨優雅的體驗，將複雜度封裝在系統內部。

### 8. 窮盡設計空間 (Exhaust the Design Space)
* **觸發情境**：面對無先例的重大架構或全新互動設計時。
* **核心規範**：設計兩次以上。在鎖定單一方案前，至少產出兩種結構上截然不同的候選方案進行客觀比對（如透過 `arena` 競賽），避免過早受限於首個直覺方案。

### 9. 打造槓桿 (Build the Lever)
* **觸發情境**：任何非平凡的多步驟操作、遷移或驗證。
* **核心規範**：優先編寫可重跑的自動化工具（腳本、Codemod、產生器或測試 Harness），而非手動逐個修改。工具本身就是可被他人審查與重跑的可靠資產。

## 二、架構設計原則 (Architecture Principles)

### 10. 領域建模 (Model the Domain)
* **觸發情境**：編寫狀態邏輯、代碼出現大量條件分支、或跨檔案重複相同的形狀假設。
* **核心規範**：將領域真實概念編碼進資料結構中（如狀態機、查找表、辨識聯合 Discriminated Union），使非法狀態無法表達 (Make illegal states unrepresentable)，徹底消滅散落各處的旗標變數與條件分支。

### 11. 邊界紀律 (Boundary Discipline)
* **觸發情境**：處理外部輸入校驗、錯誤處理或框架介面配接。
* **核心規範**：嚴格在系統邊界（CLI 參數、設定檔、網路 API、外部依賴）進行解析與驗證，業務核心內部完全信任強型別資料；業務核心邏輯保持為純函式，薄型外殼 (Thin shell) 僅負責調度。

### 12. 型別系統紀律 (Type System Discipline)
* **觸發情境**：在任何靜態型別語言中設計型別與函式簽名。
* **核心規範**：利用型別系統消除無效狀態；在邊界做 Parse 而非到處 Check；嚴格避免鬆散的 `any` 或過度依賴強制轉型。

### 13. 使操作冪等 (Make Operations Idempotent)
* **觸發情境**：設計生命週期步驟、指令或在崩潰與重試環境下運行的循環任務。
* **核心規範**：確保重複執行多次能穩定收斂到相同的最終狀態，防止部分成功導致系統陷入不一致。

### 14. 遷移呼叫方並徹底刪除遺留 API (Migrate Callers Then Delete Legacy APIs)
* **觸發情境**：引入新的內部 API 或替換舊介面時。
* **核心規範**：在同一個波次中將所有呼叫方遷移至新 API，並立即刪除舊 API 與相容層，絕不留下過渡期死代碼。

### 15. 串列化共用狀態前先做分離 (Separate Before Serializing Shared State)
* **觸發情境**：多個並發角色可能同時寫入同一檔案、分支或物件。
* **核心規範**：優先消除共用狀態（例如每個角色寫入專屬工作區或目錄），最後在讀取邊界進行合併，而非過早依賴複雜的鎖定機制。

## 三、驗證實踐原則 (Verification Principles)

### 16. 證明有效 (Prove It Works)
* **觸發情境**：完成任務並宣告交付之前。
* **核心規範**：必須透過運行真實代碼、測試套件或實機操作來捕獲客觀證據。「代碼能編譯通過」不等於「功能正確」；證據先於斷言。

### 17. 根因修復 (Fix Root Causes)
* **觸發情境**：除錯與處理 Bug。
* **核心規範**：先建立重現案例，連續追問直到觸及根本原因。嚴禁在症狀表面添加保護性補丁（Symptom guards）。若決定性的根因事實耗費了深度挖掘才找出，應主動提議增設一個低成本的常駐防護訊號（Cheap, always-on signal），讓同類問題在未來第一眼就能顯現。

### 18. 質疑前提 (Attack the Premise)
* **觸發情境**：當兩個以上基於相同假設前提的修復方案，都在同一個驗證關卡失敗時。
* **核心規範**：懷疑該「前提假設」本身，而非繼續修補方案。每次失敗的修復都是對其隱含前提的反證；在動手寫下一個修復前，必須先把共同前提用一句話寫下來，並設計直接觀察來驗證該前提是否成立。若證據推翻前提，立即轉向尋找真正的共同成因。

### 19. 解釋數字背後意義 (Explain the Number)
* **觸發情境**：在採信、報告或依據任何測量數據（加速比、效能退化、吞吐量、延遲或評測結果）採取行動之前。
* **核心規範**：追問「為什麼不是兩倍好？（Why not double?）」，從執行期剖析或系統計數器中指認出真正的限制因子（CPU 核心、鎖、磁碟、網路或壓測端本身），嚴禁只憑讀代碼猜測。同時列出並以證據排除其他可能造成該數字的假象（錯誤跳過、快取命中、未執行的惰性代碼、未調優的預設設定或背景雜訊）。報告數字時必須一併附上執行次數、波動範圍與限制因子。

### 20. 測試行為而非實作 (Test Behavior, Not Implementation)
* **觸發情境**：撰寫、修改或審查測試案例時。
* **核心規範**：只斷言呼叫方或使用者透過公開介面可觀察到的外部行為（回傳值、錯誤型別、可讀回的狀態、對外部系統產生的副作用），絕不綁定內部私有函式、呼叫順序或中間資料結構。以兩項假想修改檢驗每個測試：(1) 破壞外部行為時，測試必須失敗；(2) 保持外部行為不變僅重構內部實作時，測試必須持續通過。

### 21. 將工作拆解為可驗證單元 (Sequence Work into Verifiable Units)
* **觸發情境**：多步驟任務、大型遷移或重構。
* **核心規範**：將任務切割為若干獨立且自帶驗證步驟的小單元，完成一個並驗證通過後才推進下一個，確保每個階段提交均保持穩定。

## 四、任務委派原則 (Delegation Principles)

### 22. 守護上下文窗口 (Guard the Context Window)
* **觸發情境**：面對大量日誌、巨型檔案或多分支排查。
* **核心規範**：將粗重的大規模讀取與搜尋任務交由 Subagent 獨立完成，主對話僅保留結構化提煉後的結論，保護對話上下文不被雜訊淹沒。

### 23. 可逆工作不阻塞人類 (Never Block on the Human)
* **觸發情境**：面對低風險、可逆的實現路徑選擇。
* **核心規範**：不要向使用者詢問瑣碎且可逆的細節；主動做出合理決策並實施，呈現結果供使用者校準。僅在不可逆操作（刪除資料、破壞性變更）時暫停等待確認。

---

## 五、元實踐原則 (Meta Principle)

### 24. 結構化沉澱教訓 (Encode Lessons in Structure)
* **觸發情境**：重複提醒同一項規範或修正類似錯誤。
* **核心規範**：將教訓轉化為 Linter 規則、型別約束、自動化測試或前置腳本，依靠代碼結構強制保證，而非依賴記憶與口頭叮嚀。
