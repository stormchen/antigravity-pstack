# Maintain a Formal Verification Skill (維護形式驗證技能與模型同步)

形式驗證證明的是「它所描述之模型」的性質。當真實代碼已經改變、而驗證模型沒有隨之更新時，驗證可能繼續綠燈通過，但它證明的卻是早已不存在的舊代碼——這種「假性通過」是最危險的盲區。本技能專門用於維護由 `/create-formal-verification-skill` 生成的驗證技能（或任何針對特定代碼執行模型檢測、定理證明與驗證器的專案技能），處理因跨分支合併、未執行驗證的直接修改、或多次提交累積所造成的模型漂移（Drift）。

## 1. 四種判定結果 (Outcomes)

針對每一項形式檢查，給出以下四種明確判定之一：

- **`in sync`（完全同步）**：自上次 Sync Commit 以來，沒有任何變更影響模型所描述的行為，且檢查通過。
- **`updated`（已更新並通過）**：代碼結構已改變，驗證模型已更新為描述最新代碼，且檢查通過。
- **`bug`（發現真實缺陷）**：驗證模型準確描述了當前代碼，而當前代碼違反了核心性質。這是代碼的真實缺陷，而非模型漂移。
- **`blocked`（受阻）**：無法將檢查與代碼對齊或無法執行，必須具體說明原因。

（註：一項檢查可以同時是 `updated` 與 `bug`——亦即模型更新至反映最新代碼後，發現最新代碼違反了安全性質。）

## 2. 修改範圍限制 (Edit scope)

執行維護期間，**僅限修改驗證相關檔案**（模型檔、Harness、性質定義檔與驗證技能 `SKILL.md`）。除非使用者明確要求，否則**嚴禁修改產品代碼**。當某項性質在最新代碼上驗證失敗時，嚴禁為了湊綠燈而削弱性質或放寬模型假設，必須如實報告失敗。

## 3. 執行步驟 (Pass)

1. **盤點現有形式檢查 (Find the checks)**：
   找出專案中所有的形式驗證技能（或使用者指定的那一個）。收集每項檢查的：驗證性質（Property）、涵蓋代碼路徑、邊界與假設、執行指令，以及上次確認同步的 **Sync Commit**。若找不到任何形式驗證技能，請停止並指引使用者先執行 `/create-formal-verification-skill`。若技能未記錄 Sync Commit，則以最後一次修改驗證檔案的 Commit 作為基準，並在報告中註明。
2. **先跑一次現狀基準 (Run it as it is)**：
   在修改任何東西前，先照原樣跑一次所有檢查並記錄結果。此時通過不代表新代碼沒問題（只代表舊模型依然自洽）；此時失敗可能是模型漂移或真實 Bug，留待步驟 5 判定。
3. **逐一審查受保護代碼的變更 (Read every change to covered code)**：
   比對從 Sync Commit 到當前 HEAD 之間，所有涵蓋檔案的 `git diff` 與 commit 訊息。同時留意**搬移或重構的代碼**（被改名、拆分或移至其他檔案的函式依然屬於受保護範圍）以及**新觸及受保護狀態的代碼**（例如新增了一個寫入相同欄位的函式）。將每處變更歸類為以下四種之一：
   - **無影響 (No effect)**：排版、註解、或模型未涵蓋的無關分支（須對照模型本身確認，不可只看 commit 訊息）。
   - **模型已不再反映代碼 (Verification no longer describes the code)**：原本不可分割的單一步驟變成了兩步、新增或移除了分支、檢查位置移動、出現到達受保護狀態的新路徑、或數值範圍改變。**此時必須更新模型或 Harness。**
   - **代碼承諾蓄意改變 (Promise changed on purpose)**：代碼對外承諾的性質被刻意調整，且在文檔註解、測試、Changelog 或 Commit 訊息中有明確證據支持。**此時必須更新性質定義，並引用該證據。**
   - **承諾可能已被打破 (Promise may be broken)**：代碼改變了行為，但沒有任何證據顯示這是蓄意的規格變更。將隨後的驗證失敗視為**潛在 Bug**。
4. **根據代碼更新模型，而非根據結果湊答案 (Update from the code, not from the result)**：
   在重新執行前，對照最新源碼更新模型與 Harness，確保每個部分都重新對應回真實代碼，並維持原子步驟的一對一映射。**嚴禁為了讓檢查通過而反向捏造模型。** 只有在確認「承諾蓄意改變」時才修改性質定義（須同時記錄舊表述、新表述與證據）。除非變更使舊邊界失效，否則維持原有邊界（Bounds）；若不得不縮小邊界，必須在報告中明確聲明。
5. **重新執行並裁決結果 (Rerun and judge each result)**：
   - **若通過 (Pass)**：更新後的模型可能因為寫錯而喪失了報錯能力（Vacuous Pass）。請在最新代碼或模型上做一次針對該性質的臨時破壞（例如拿掉新加的檢查或對調步驟），**確認檢查能成功抓到並報錯**，再將臨時破壞還原。
   - **若失敗 (Fail)**：將反例（Counterexample）對照真實源碼一步步重演。若其中某一步在真實代碼中根本不可能發生，代表模型有誤，請修正模型並說明原因；若每一步在真實代碼中都能發生，這就是**真實代碼 Bug**——請指出引入該 Bug 的 Commit、用代碼術語列出反例步驟序列，並用一句話說明其危害。若能用簡短測試在真實代碼上重現該 Bug，將其作為證據附在報告中（不提交至產品代碼）。
6. **更新驗證技能元數據 (Update the verify skill)**：
   更新技能檔中的涵蓋檔案清單、執行指令、邊界假設與 **Sync Commit**（推進至本次檢查的 HEAD Commit；若狀態為 `blocked` 則不得推進）。最後以接手 Agent 的視角照著技能步驟跑一次，確保所有指令流暢無誤。

## 4. 維護報告 (Report)

向使用者清晰報告每項檢查的：
- **最終判定**（`in sync` / `updated` / `bug` / `blocked`）與審查過的 Commit 範圍。
- **驗證模型修改內容與原因**（代碼結構改變，或附帶證據的規格蓄意變更）。
- **重跑結果與反證測試**（用於證明更新後的檢查依然具備報錯能力的破壞測試）。
- **發現的真實 Bug**（以白話代碼步驟呈現反例、危害說明、以及引入問題的 Commit）。
- **尚未涵蓋的缺口**（包含本次新增但尚未納入驗證的相關代碼）。

將形式驗證的更新獨立提交為一個純驗證變更，與任何產品代碼修復分開。
