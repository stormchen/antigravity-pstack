# Benchmark Checklist (效能基準測試檢驗清單)

當你產出任何效能數據時（PR 前後對比、效能退化報告、Hillclimb 測試 Harness、或套件與設定選型），在報告或依此採取行動前，必須用**真實執行產生的證據**回答以下每一個問題，嚴禁僅憑閱讀源碼猜測。

若使用者只是要求快速估算一個數量級（Ballpark），跑一次即可，但仍須檢查**問題 4（是否有錯）**與**問題 7（工作是否真的有執行）**，並明確聲明這只是單次執行結果。**方案選型（A vs B）永遠不能用粗略估算敷衍。**

## 執行測量前的準備

- **寫下預期主張**：用你準備寫進報告的原話寫下預期結論（例如：「在 6 萬筆資料集上，匯出功能的 p50 耗時加快了 30%」）。以下七個問題專門用來檢驗這句話。
- **閱讀測量腳本**：確認它計時了哪個區段、計數了什麼、又忽略了什麼。
- **檢查機器負載與核心數**：確認系統當前背景負載與 CPU 核心數。若機器繁忙且無法停止背景程序，必須將對照組與實驗組**交錯執行（A, B, A, B...）**，讓雙方承受相同的背景雜訊，並在報告中註明。

## 七大檢驗問題 (The Questions)

1. **為什麼不是兩倍快？(Why not double? — 指認限制因子)**
   找出當前的系統瓶頸（Limiter）。在**不計入正式報告的獨立執行**中進行 Profiling（因為 Profiler 與 Tracer 本身會拖慢速度）。觀察各進程 CPU 使用率、執行期 Profiler（如 `node --cpu-prof`、`py-spy`）、I/O 等待與系統呼叫次數，將熱點映射回源碼。同時監控壓測產生器（Load Generator）：若壓測端先飽和，你測到的是壓測器而非目標系統。若某項改動沒有改變數據，限制因子會解釋原因，在宣稱改動無效前必須先找出它。
2. **雙方是否都經過同等調優？(Was it tuned?)**
   每一方都必須以正式環境（Production）的方式運行：Release 建置、正式環境參數、批次與交易設定、連線池、符合正式環境冷熱狀態的快取，以及相同的版本與資料集。若其中一方使用預設值（例如每筆資料獨立 commit、Debug 建置、漏建索引），你比較的是「設定差異」而非「實作優劣」。在選出贏家前，必須將未調優的一方調好並重測；若無法調優，則不得據此宣布贏家。
3. **是否違反物理與數學極限？(Did it break limits?)**
   動手算算術（阿姆達爾定律 Amdahl's Law）：將每秒位元組數與磁碟/網路頻寬對比、將每秒操作數乘以單次成本與 CPU 核心數對比、將省下的時間與被修改模組原本佔用的時間對比。**砍掉一個原本只佔總時間 10% 的步驟，整體最多只能快約 11%。** 任何超越物理或算術極限的驚人加速，測到的往往是快取命中、空操作（no-op）或 Bug。
4. **過程中是否發生錯誤？(Did it error?)**
   統計失敗次數與非成功回應，並驗證輸出內容的**正確性**（而不只是有輸出）。拒絕請求（Rejection）通常極快，而超時（Timeout）與重試則極慢。若壓測腳本沒有統計錯誤率，必須先補上錯誤計數。
5. **結果是否可穩定重現？(Does it reproduce?)**
   每一方至少執行 **5 次以上**，並採用交錯順序（A, B, A, B...）以抵銷預熱（Warmup）、延遲初始化、快取與系統漂移的影響。報告**中位數（Median）與全距（Range）**。若前後差距小於多次執行間的波動範圍，代表「無顯著差異（No measurable difference）」。差距極接近時應使用統計檢定。
6. **這項改善在端到端是否重要？(Does it matter?)**
   除了微基準測試（Micro-benchmark）外，必須在真實資料量與並發度下測量使用者實際等待的**端到端路徑（End-to-End）**，並報告微基準部分佔整體的比例。一個只佔請求 1% 時間的輔助函式，就算最佳化到零耗時，整體請求最多也只會快 1%。
7. **被測量的工作真的有發生嗎？(Did it even happen?)**
   確認目標工作確實發生在計時區間內：請求真的抵達伺服器、資料行真的寫入磁碟、位元組真的被讀取、且程式碼真的使用了運算結果。惰性求值（沒人迭代的 Generator、沒人 `await` 的 Promise、被 JIT 編譯器消除的死算式）以及提前超時，都會製造出「耗時極短但工作根本沒發生」的假數據。

## 報告規範 (Report)

- **結論先行**：明確給出裁決——**變快（Faster）**、**變慢（Slower）**、**無顯著差異（No measurable difference）**或**無法下定論（Inconclusive）**。
- **附帶完整證據鏈**：報出數字與單位、執行次數、波動範圍與限制因子。例如：`p50 由 41 ms 降至 33 ms（每組交錯執行 7 次之中位數，改善後範圍 32–35 ms，受限於單核 JSON 解析）`。
- **誠實標記 Inconclusive**：若宣稱有差異卻指不出限制因子、任一方處於未調優狀態、或無法確認問題 4 與問題 7，必須將結論標為 `Inconclusive` 並點出缺失環節。
- **保持 PR 簡潔**：PR 正文僅放一個核心指標數字（遵循 `opening-a-pr.md`），詳細的多輪數據、範圍與剖析證據放入關聯產物或紀錄檔中。
