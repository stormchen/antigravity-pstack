# Correct (結構化糾偏與防呆固化)

當操作者在此儲存庫中反覆糾正 Agent 犯下同類錯誤時，請直接改造儲存庫，讓下一個 Agent **在結構上根本無法再犯**。

假設每一位貢獻者都是只看當前打開的幾個檔案、直接複製最近範例、並走最短編譯通過路徑的 AI Agent。將儲存庫設計成「從單一檔案看起來正確的寫法，對整個儲存庫而言也是正確的」。

## 1. 找出重複錯誤類別 (Find the mistake classes)

首先閱讀近期的 commits、reverts、PR 審查意見、Agent 規範檔（如 `AGENTS.md`）以及解釋 workaround 的註解。將錯誤歸納為具體類別。同類錯誤只要發生過**兩次以上**即列入處理。

## 2. 在最高有效層級根除錯誤 (Fix at the highest level that works)

依循以下優先順序由高至低防堵：

1. **透過架構徹底消除 (Eliminate with architecture)**：讓每份狀態只有唯一擁有者（Single Owner），每種任務只有唯一支援的做法。隱藏模組內部細節，使錯誤的跨層匯入直接在編譯期失敗。將需要手動同步的多處清單替換為單一事實來源（Single Source of Truth）。徹底刪除會誤導 Agent 複製的舊寫法與死代碼。
2. **透過型別系統與 Linter 強制約束 (Enforce with types & lint)**：利用強型別讓非法狀態根本寫不出來。若錯誤代碼仍能通過編譯，新增一條 Linter 或 CI 檢查，且其**報錯訊息必須直接點名應改用的正確檔案、型別或函式**。若舊代碼中該反模式已廣泛存在，則設定為「禁止新增更多此類寫法」。
3. **測試外部行為 (Test the behavior)**：遵循 **principle-test-behavior-not-implementation**，修復或刪除那些「功能壞了卻依然通過」或「只改內部實作就失敗」的脆弱測試。
4. **最後才寫文件或規則 (Write docs or agent rules last)**：僅針對無法由程式自動判定的主觀裁量事項撰寫文字規則。因為當 Agent 漏讀文件時，文字規則不會觸發任何報錯。

## 3. 實作修復並證明有效 (Fix and prove)

針對最高頻的錯誤類別進行修復，每個類別獨立一個 commit。**拿過去真實發生過的歷史錯誤案例，證明你新增的檢查確實會報錯失敗**，接著在本機與 CI 跑通相同指令。若極少數情況必須豁免，豁免標註必須寫在違規行上，並附帶具體理由、到期日與人類核准紀錄。

## 4. 維護規則與執行機制對照表 (Keep the rule table)

在 Agent 規範檔案中維護一張對照表，將每一條文字規則與其背後的「強制執行機制（型別、Lint、測試）」配對：
- 當操作者再次糾正你時，修好當下錯誤並補入對照表。
- 若某條規則早已寫在文件裡，卻沒有任何自動化機制強制執行，代表文字規則已經失效——請在同一次變更中將其升級為上述第 1~3 層級的結構化檢查。
- 一旦某個錯誤在架構或型別上已完全不可能發生，即可將該條文字規則從文件中移除。

**回覆格式**：列出每個錯誤類別及其歷史證據、你選擇防堵的層級，以及為何無法在更高層級解決的原因。
