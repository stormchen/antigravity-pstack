# Ketchup (離席進度與決策同步看板)

為使用者快速同步自他們在 `/ketchup` 之前發出的最後一條訊息以來，這個對話中發生的所有實質進展，並協助他們理解每項變更的意義，而不僅僅是報告進度百分比。接著，完整列出每一個等待他們拍板的決策項（Action Items），讓他們僅憑這則回覆就能直接做出決定。系統通知與 Subagent 回報不算使用者的訊息；假設使用者只記得自己說過的最後一句話，對那之後發生的事一無所知。

採用 [`/bro`](../bro/SKILL.md) 的說話語氣（但非其任務）：用大白話、短句、零行話，就像同事剛從會議回來時你幫他快速抓重點一樣。說明「對使用者而言改變了什麼」，而非「你底層怎麼實作的」。說「測試都過了」，不要說「CI 綠燈」。除非使用者做決定時需要用到，否則省略 commit hash、檔案路徑、指令、build 編號與測試數量。用使用者認得的名稱稱呼 PR、分支或 Subagent，不要用自己發明的代號。如果某個事實需要脈絡才聽得懂，就把脈絡補上，否則直接省略。

## 1. 蒐集變更事實 (Gather what changed)

本回合保持**純唯讀**。僅使用手頭已有的素材製作視覺圖表：不修改代碼、不啟動應用或背景任務、不對外發送任何訊息。彙整自使用者上次訊息以來你完成的工作、各 Subagent 的回報，以及對話中其他人的訊息。檢查對話觸及的每個 PR、CI 任務或 Subagent 的最新狀態。將你要展示的每個數字與原始事實核對，若有修正請明確說明。

**待決策事項 (Action Item)** 是指只有使用者本人能做的決定或步驟，例如產品取捨、核准、不可逆操作，或你缺乏權限的操作。包含任何仍在等待使用者回應的事項（即使是在他們最後一條訊息之前提出的）。你自己還能繼續推進的工作不算待決策事項。切勿為了湊版面而捏造問題。使用者沒要求且工作本身也不需要的步驟不算待決策事項（除非它是不可逆且正等待使用者確認，此時僅用一行文字說明，不附圖）。

同一個決策可以涵蓋多個項目（例如等待合併的一組 PR）。針對每個項目，蒐集其連結、對使用者的實質改變、你推薦選項背後的證據、風險，以及你的建議選項（Your Pick）。若決策所需的某項事實尚不清楚，誠實標註「未知（unknown）」。沒有連結就省略連結。

## 2. 撰寫回覆 (Write the reply)

把篇幅花在「需要拍板的決策」上，而不是講述工作故事。
- **進展摘要**：不計圖片，控制在 **100 字以內**（發生的事越少就越短）。對使用者沒有實質影響的工作直接略過。
- **決策事項**：每個項目約 **30 字**。回覆長度隨決策項目數量自然增長：2 個項目總計遠低於 150 字，30 個項目則會長得多。**絕不為了湊字數上限而刪減或壓縮待決策項目**：不可只報數量不列清單，也不可只貼連結代替項目說明。連結可用於補充深度，但單靠回覆本身必須足以讓使用者做出決定。

### 回覆結構：

1. **開門見山（1 句短話）**：點出目前有什麼正等待使用者決定，或者直接說「目前沒有需要你拍板的事」。若期間什麼都沒發生且沒有待決策事項，講完這句就結束。
2. **展示進展（視覺優先）**：
   - 先內嵌工作期間產出的截圖與影片，接著放入解釋變更的架構圖或流程圖。
   - 針對使用者要求的每件事，各用一條簡短列點總結：結果如何、目前是已完成、執行中、失敗或尚未檢查。
   - 用口語自然的方式寫每一行：寫「搜尋變慢是因為漏建了索引」，不要寫「搜尋審查：完成」或「慢速搜尋：缺少索引」。順手發現並修好的 Bug 也要點出。每一行單獨看都必須成立。還在等使用者決定的事絕不標為完成，且待決策清單會寫的內容不在這裡重複。
   - 摘要下方最多用三行短句補充會改變使用者認知或後續行動的關鍵事實，再用一行點出你自己接下來還能繼續做的剩餘工作。
3. **列出待決策事項 (Action Items)**：
   - 明確提出需要使用者拍板的動作（如：合併、核准、二選一），並給出**你的建議選項 (Your Pick)**。你認為應該先做的步驟、必須最先發生的前置條件、以及不可逆的操作，都放進你的建議中。附上相關 PR、Issue 或 Subagent 的編號或連結。
   - **單一項目決策**：用一個列點寫完：決策問題、你的建議、對使用者的改變、支持建議的證據、以及風險（項目名稱只提一次）。
   - **多項目共用決策**：先寫一次決策問題與整體建議，接著依**風險由高到低**為每個項目各列一點：連結與名稱、對使用者的改變、證據、風險（僅在個別項目建議與整體不同時才特別標註）。即使風險很低也要寫明（例如：「低風險：僅調整按鈕配色」）。只有在等待的代價不只是延遲（例如會錯過死線或遺失資料）時，才特別說明等待成本。
   - **多方案取捨決策**：列出評估過的每個選項，說明各選項能為使用者帶來什麼好處、付出什麼代價，以及目前的現狀。這些代價本身就是決策風險，無須另外重複寫風險行。若上方截圖展示了不同方案，直接在對應截圖下方寫出該方案的優劣得失。

## 3. 視覺化規範 (Visuals)

視覺元素是指真正的圖像：截圖、錄影、Mermaid 圖表、數據圖表或生成的圖片。**Markdown 表格不是視覺元素**（就算有 Before / After 欄位也一樣）。

當某件事用圖比用文字更容易一眼看懂時，就畫圖：系統運作方式、PR 堆疊或依賴鏈及其各自狀態、修復前後對比、或並排的方案比較。**絕不**把狀態清單、待辦列表或彼此沒有連線關係的方框畫成圖。同一個事實絕不在文字與圖表之間重複出現兩次。

每張圖必須小巧到能一眼掃完：**最多 6 個節點方框，每個方框最多 8 個字**。標籤用人話寫（例如「檢查權限」），不要寫標籤式的「Tests: pass」。需要一整句話才能講清楚的事實應放進內文。

可見的畫面變更必須直接內嵌截圖或影片，不能只給連結。若畫面變更尚無截圖，在該行標註「尚無截圖」並直接描述畫面變化。只根據真實數據繪製圖表，絕不捏造數字，也絕不憑空繪製未曾實際擷取的畫面。只連結真實存在的產物。
